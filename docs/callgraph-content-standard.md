# 调用图内容说明规范

## 目标

调用图不仅要证明“谁调用了谁”，还要帮助第一次接触项目的读者建立运行时心智模型。
节点和关系说明应让读者不打开源码也能先回答：

1. 当前步骤为什么存在；
2. 它接收什么状态、请求或结果；
3. 它做了什么关键决策或副作用；
4. 执行如何进入下一步、分支、汇合或下一轮循环。

本规范约束生成模型和人工编辑，不增加新的 schema 字段，也不使用自动文字质量校验器。
现有结构、源码位置和证据校验仍然是事实边界。

## 基本原则

- **先事实，后解释**：先基于源码说明真实职责，再解释它在整条链路中的意义。
- **局部与全局同时成立**：描述既不能只是函数注释，也不能脱离当前图泛谈架构。
- **关系说明变化**：不要把节点名换一种说法；要说明控制权、数据、条件或状态如何变化。
- **不为详细而猜测**：源码不能支持的运行时结论不写。省略中间节点时明确说明这是图级压缩。
- **摘要可扫读，详情有信息**：通常使用两句或两个分句；没有新信息时不要机械凑字数。

## 图谱说明

图级 `description` 应交代：

- 场景入口和最终目标；
- 覆盖的关键阶段或边界；
- 图中特别需要关注的分支、循环、异步或跨进程关系；
- 必要时说明没有覆盖的范围。

推荐写成 2–3 句连续说明，而不是功能列表。

## 场景阶段

0.4 `phases` 是调用图内部的可选说明与兼容数据。独立场景页按
`docs/scenario-authoring.md` 单独生成，不要求调用图补充阶段或下钻映射；主工作台不再
由 phases 生成场景拓扑。仅在阶段说明有助于理解调用图本身时保留它。

- 阶段标题使用用户场景语言，例如“准备回合上下文”“执行外部工具”，不使用 crate 或函数名。
- `summary` 说明这一阶段把什么输入转成什么结果，以及可能进入哪些后续路径。
- `order` 只提供稳定布局顺序，不宣称阶段严格线性执行，也不替代真实边。
- 节点通过单个 `phaseId` 归属阶段；不要维护阶段专属节点清单或额外连线。
- 跨阶段分支、汇合和回环继续写在真实边的 `flowKind` 中，不生成另一套调用关系。
- 互斥结果必须拆成独立阶段，例如“压缩上下文”和“完成本轮”不能合成一个阶段；否则拓扑
  会把条件路径误读为固定步骤。
- 面向多个结果的阶段使用“判断什么”的标题，分支和终点使用“产生什么结果”的标题，避免
  只写内部处理动作。
- 简单、单阶段调用图不添加阶段，避免为了格式完整而制造无意义导航。
- 阶段数量由执行语义决定，不设固定上限；难以扫读时先改善说明或按自然边界拆分阅读内容，
  不为数量目标省略调用链中的关键分支、回环或终点。

## 节点说明

### `role`

`role` 是可快速扫描的职责标签，使用名词短语，例如“采样前压缩门禁”“审批来源协调器”。
不要只写“处理器”“调用方法”或重复函数名。

### `description`

节点说明优先包含两层信息：

1. **本地职责**：输入、关键行为、输出或状态变化；
2. **链路意义**：它承接哪个阶段，为什么在这里出现，之后把流程推进到哪里。

对特殊拓扑补充：

- 入口节点：说明它如何把外部事件转成系统内部流程；
- 分叉节点：说明根据什么选择后续路径；
- 汇合节点：说明哪些结果在此重新进入共同主干；
- 循环节点：说明每轮推进的状态以及继续或退出条件；
- 终点节点：说明本图在此得到什么结果，而不是笼统写“流程结束”。

不要求每个节点机械列出所有上下游名称。只在上下游关系能帮助读者理解时引用关键节点。

## 同一调用者内的执行顺序

当同一个方法会按确定顺序调用多个下游方法时，在这些调用边上填写从 `1` 开始的
`order`。序号表达的是一次基础流程中的执行先后，不是节点重要性，也不是 JSON 数组顺序。

- 只为能够由源码或可靠运行语义确认的顺序编号。
- 同一 `from` 节点下的顺序从 `1` 递增；调用图允许省略未建模的中间调用，因此不强制连续。
- `branch / fallback` 是候选路径，不用 `order` 暗示各分支都会依次执行。
- 并发、`spawn`、回调完成顺序不确定时不填写 `order`，在边描述中明确并发或顺序未定义。
- 多条边没有 `order` 时保持确定性布局，但不应把画面位置描述成严格运行时顺序。

示例：

```json
{
  "id": "turn-to-prompt",
  "from": "run-turn",
  "to": "build-prompt",
  "kind": "direct",
  "order": 2,
  "file": "src/turn.rs",
  "line": 138
}
```

## 调用关系说明

边的 `description` 要回答“为什么从这里到那里”，至少提供下列信息中真正适用的一项：

- 触发条件或前置状态；
- 传递的请求、数据、配置、认证或执行结果；
- 同步委托、异步任务、回调、Trait 分发、远程边界等调用方式的影响；
- 分支选择与兄弟路径的差异；
- 分支完成后的汇合位置；
- 循环回到哪里、下一轮读取什么，以及如何退出。

不同语义的写法：

- `normal`：说明前一步完成了什么准备，后一步接管什么工作。
- `branch / fallback`：说明选择条件和该路径承担的职责。
- `merge`：说明哪条支路完成后回到哪个共同阶段。
- `loop-back`：说明本轮产生的结果如何触发下一轮。
- `loop-exit`：说明退出条件和退出后得到的状态。
- `data-flow`：明确传递的是数据或状态依赖，不伪装成同步函数调用。
- `spawn / async-boundary / callback`：说明调用栈或等待关系发生了什么变化。
- `remote`：说明协议或进程边界，以及请求与响应承担的作用。

## 反例与改写

节点反例：

> 处理模型请求。

改写：

> 组合历史、工具目录和模型配置后发起一次采样请求；它把已经准备好的回合上下文转换为
> provider 可消费的 Prompt，是进入模型传输层前的编排边界。

关系反例：

> 调用 `run_turn`。

改写：

> 普通任务把标准化输入和 TurnContext 交给 `run_turn`；从这里开始，采样、工具续跑与
> 上下文压缩都由同一个回合状态机协调。

回环反例：

> 继续循环。

改写：

> 工具结果写回会话历史后，`needs_follow_up` 触发下一次采样；新一轮会携带刚产生的工具
> 输出，而不是从原始用户输入重新开始。

## 禁止的写法

- 只重复 label、role、函数名或“调用某方法”；
- 使用“负责相关逻辑”“进行处理”“完成操作”等没有对象和结果的空泛表达；
- 把 `data-flow` 写成确定的同步调用；
- 把可能发生的分支写成每次都会执行；
- 为了显得完整而虚构返回值、线程、锁、缓存或失败行为；
- 在每个节点后机械追加相同的“然后进入下一节点”。

## 生成和修改流程

生成模型在创建或修改 `graphs/**/*.json` 前必须：

1. 完整阅读本规范和 `docs/control-flow-semantics.md`；
2. 阅读目标源码和现有证据，不只依据函数名推断；
3. 先确认图的场景边界、入口、主干、分支、汇合和回环；
4. 需要阶段说明时，再划分语义阶段并给节点标注归属；独立场景页不要求调用图提供阶段；
5. 先写节点本地职责，再从整图视角补充链路意义；
6. 最后通读全部边，检查相邻描述是否重复、分支条件是否冲突、回环是否说明下一轮状态；
7. 运行现有结构与源码校验，但不使用字数或关键词判断文字质量。

源码位置有效不等于证据正确。代码改动后需确认节点起始行仍是声明的符号，`endLine`
仍覆盖需要解释的范围，精确边的行号仍是对应调用点。说明和 `callSiteNote` 中的行号也要
同步；不能用旧提交标识描述已变化的工作区。项目自身示例由
`node tests/project_evidence_test.mjs` 检查定义和精确调用锚点，其他项目仍需结合源码核对。
`phase.order` 仅是布局顺序，最大值不证明业务终点；结构无出边也不证明运行时结束。

两类图的生成入口见 [`graph-authoring.md`](graph-authoring.md)。场景页另用语义 JSON
生成，不要求调用图生成模型制作 HTML/SVG 或维护跨页映射。

## 人工复核清单

- 隐藏函数名后，读者还能说出这个节点为什么存在吗？
- 只看边说明，读者能判断控制权或数据发生了什么变化吗？
- 分支说明能区分不同路径，而不是写成同一句话吗？
- 回环说明是否交代本轮结果和下一轮起点？
- 描述中的每个具体事实都能被源码、字段或相邻图结构支持吗？
- 删除一句话后如果信息没有减少，应删除该句。

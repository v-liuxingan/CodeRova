# LSP 采集策略评估与优化

本页保留阶段性评估；当前操作见 [工作台 Skill](skills/callgraph-workbench/SKILL.md)。
V2 页面使用内存草稿，新增节点无须先保存即可续采，预览不写文件；采纳/保存才写入。
下文立即保存检查点的描述仅适用于旧直接 API，不适用于 V2 草稿流程。

## 2026-11-02：有界并发与单节点失败隔离

当前 CLI 和页面续采共用 `analysis/collector.rs`。`analysis/lsp.rs` 的独立读循环维护
请求 ID → 响应接收方，独立写循环保证消息帧不被取消或并发写入截断。服务器通知与反向请求
由读循环处理。配置解析集中在 `analysis/config.rs`，语言适配器不再拥有遍历或保存策略。

本地配置 `collection` 默认 concurrency=4、requestTimeoutSeconds=15、maxRetries=3。
并发可设 1–32，已验收 4/8/16；单次查询超时可设 1–300 秒，重试可设 0–3。
每次尝试使用新 ID；超时结束本地等待，发送 $/cancelRequest，旧 ID 的迟到响应丢弃。
服务器不保证响应取消，因此不能承诺服务端物理计算被立刻停止。初始化和索引等待有独立超时。
参数/协议错误不重试；超时和可重试服务器内部错误最多初始+3次尝试。坏帧、断流使会话失效，
不能在损坏的字节流上继续查询。任务取消仍销毁会话，不把未完成租约放回热缓存。

调度按广度优先前沿排序后占用预算，同一前沿内最多 N 个工作任务，完成即合并和写检查点。
该层结束后才调度下一层，以保证响应先后不改变同深度的预算选择；这仍有层间同步等待。
图有单一写入者，不并发修改节点/边。最终输出顺序固定，不把返回顺序解释为调用顺序。
查询失败的节点保留 pendingNodes 和带节点 ID 的 issues，本轮不再次调度；其他分支继续。
实现查询失败时保留已成功获取的直接调用，并把调用方保留为未完成，不假称全部查询成功。
尚未知的下游不能伪造节点；只有已发现但未查询的节点才有明确未完成标记。

验证证据：`tests/lsp_parallel_test.py` 使用真实 CLI/stdio，在 4/8/16 下比较完整 JSON，
覆盖乱序、迟到、永不回复、瞬时和持续内部错误、重试上限、部分成功与坏帧断流；
`tests/lsp_session_test.py` 验证取消、源码/配置变更与热会话安全性。
真实 Spring refresh 两层、预算 40 的三次独立进程实测分别 14.345/12.967/12.724 秒，
均产出 177 节点、229 关系、19 个已查询符号；三份完整 JSON 相等。
66 条 issues 全是深度边界，没有新增解析错误。复用磁盘索引，运行顺序为 4→8→16，
不是随机顺序基准；差异包含缓存影响，不能推断全量采集加速倍数。
原始图与日志在 `target/spring-parallel-20261102/`，协议测试结果在 `target/lsp-parallel-results.json`。
本轮没有重复执行此前 1000 查询的深层 Spring 验收；大范围 JDT 并发收益仍需后续测量。

## 2026-11-02：减少跨项目重复索引

原先只有一个空闲会话位置，项目 A → B → A 会启动三个服务器。现在保留最多两个热会话，
按项目规范化路径和语言隔离；回到未变化的 A 复用原进程。新增第三个项目时淘汰最久未归还的会话，
每个会话仍在闲置 5 分钟后回收。代价是可能同时保留两个语言服务器的内存。
平台仍只接受一个采集/入口校验任务，不引入并发查询或跨会话复用 opaque data。

确定性 HTTP/stdio 集成验证：A/B/A 仅启动两个进程，继续往返三轮不新增进程；
第三项目淘汰 LRU，源码修改、配置修改、取消和进程死亡后均重新初始化。
这是消除重复初始化的验证，不是 Codex/Spring 冷启动提速百分比。

后续性能验证优先级：

1. 在同一 Codex/Spring 入口分开记录冷初始化、索引等待、热续采和检查点耗时。
2. 针对大图检查每节点全图复制/检查点及查找成本，维持冲突检测和停止恢复语义。
3. 评估内容指纹扫描成本；不能用仅比较 mtime 的缓存替换内容校验。
4. 再评估有界并发；先建立响应分发与取消安全性，不能直接并行现有串行读写。

## 2026-11-02：源码位置校验去重

续采每处理一个符号都会校验当前图。原实现对每个节点和精确调用点分别读取文件、统计行数，
同一个文件在一次校验中被反复读取。现在每次校验为每个文件只读取一次，缓存存在性与行数；
每个节点/调用点仍单独产生诊断，下一次校验重新读取，缺失与不可读文件不会被当作成功。
未降低校验频率、延迟检查点或改变草稿冲突检测。

本机 debug 二进制，CLI validate --json，既有真实图各运行三次，包含进程启动、图读取和报告输出：

| 图 | 源码位置数 | 改前秒数 | 改后秒数 |
| --- | ---: | --- | --- |
| Codex CLI 启动 | 5605 | 1.364 / 1.166 / 1.271 | 0.188 / 0.178 / 0.172 |
| Spring context refresh | 455 | 0.144 / 0.105 / 0.107 | 0.060 / 0.056 / 0.056 |

两张图改前/改后完整 JSON 校验报告相等。以上是同机器连续运行的校验耗时，未清空系统缓存，
不是 LSP 冷启动或端到端采集加速比例。原始对照在本机 target/validation-before.json、
target/validation-after.json；用户图未重写。
完成采集的 INFO 日志增加 validation_ms、checkpoint_ms，配合已有初始化、索引等待与
DEBUG 请求耗时，后续可区分平台开销与语言服务器开销。失败/取消不产生完成汇总。

## 本轮实现

范围为 Rust 分析器、CLI 与协议集成测试。图 JSON/HTTP 字段不变，继续用 pendingNodes
表示未采集下游，issues 区分原因。前端无需新协议适配。默认不主动排除任何项目内路径。

### 主动排除

`analyze` 增加可重复的 `--exclude-path`，接受项目内相对文件或目录，例如：

```powershell
# 将这些参数追加到原 analyze 命令；仅在确认目录不属于本次理解目标时使用
--exclude-path vendor --exclude-path tests
```

规则按路径组件匹配，vendor 不匹配 vendor_extra；不支持 glob、绝对路径或 ..。
使用源码规范化后的项目相对路径匹配，大小写按实际路径字符串匹配。
排除仅停止下游遍历，已发现的边界节点和所有入向调用点仍保留，并明确记录主动排除原因。
入口被匹配时也保留入口，报告其下游待分析。该选项不会控制 rust-analyzer 的初始索引，
不能宣称能降低全部索引耗时。它可能切断通往其他目录的可达路径，需在覆盖说明中审阅。

### 性能与失败隔离

- 一次采集内按 URI 缓存项目相对路径解析（含失败），减少反复 canonicalize；不跨运行缓存。
- 保留 BFS 和符号去重，每个已发现符号最多发起一次出向查询；循环不会无限递归。
- 完整 JSON-RPC 错误响应及格式错误的调用数组只影响当前符号，其他排队分支继续查询。
- 超时、断流、无效帧不能安全恢复读取边界，仍停止会话，记录剩余队列未查询原因。
- 深度边界与预算耗尽分别记录，null 不等于空数组，查询成功不等于语义完整。

未进行本轮真实 rust-analyzer 前后耗时对比，不能把消除重复文件系统操作表述为已量化提速。

## 后续优先级

1. 完善源码版本绑定的检查点（基础页面续采已实现）。保存原始 LSP item 的 opaque data、项目/源码指纹和服务器版本；
   旧会话 item 不能未经验证直接复用。断点恢复应重新准备失效符号，不能仅保存节点 ID。
2. 将排除、深度、预算、null、失败拆为结构化边界原因，并记录初始化、索引、请求耗时。
   当前 issues 可审阅，但不适合大规模自动统计；此项需要完整契约迁移与前端筛选支持。
3. 有界并发需要独立读循环和按请求 ID 分发、取消及进程退出处理；先测服务器吞吐，
   不能把当前串行读写 Session 直接放进并发任务。并发数应可配置并受总预算约束。
4. 引入可选可信项目完整度配置：cargo features、target、构建脚本和过程宏。
   当前禁用构建脚本/过程宏，生成代码、条件编译和宏目标可能缺失；开启会执行项目代码，
   必须由使用者明确选择，不应静默改变默认值。
5. 跨项目边界目标、动态分发、函数指针和回调需要不同解析策略与证据等级。当前项目根外
   目标只记录 issues，不生成节点；扩大深度无法补齐这些关系。
6. 同步执行顺序属于 AST/控制流分析，不能从 outgoingCalls 返回顺序或源码行推导 order。

## 页面采集与人工入口（已实现）

选择真实叶子节点后，在节点右键菜单或右侧栏点击“继续采集”。只有 pendingNodes
中且没有原始出边的节点可启动，视图收起不改变资格。全图采集按钮已移除。
本轮预算默认 100，可设置 1–1000；这是资源预算，不是图的总量上限。
任务区集中展示状态、停止、预览、采纳保存和放弃。左右侧栏从与画布的边界独立收起。

“添加节点”打开源码选择器：选择或输入项目内 Rust / Java 文件，在复用的 Monaco 编辑器
中搜索、点击行号或代码行，再校验该行所属函数。无需填写列号、符号 ID 或 LSP 参数。
空白行、无法解析的符号、未知文件、校验后变化的源码会被明确拒绝。文件列表排除构建
和依赖目录，拒绝项目外路径，单文件上限 2 MiB。

校验使用 documentSymbol 定位包含该行的函数/方法，再用 prepareCallHierarchy 确认身份。
新入口使用暖色节点和人工虚线连接；确认的是函数身份，不是消息路由或运行时调用关系。
可以补充消息名及关联说明。添加后可在同一草稿从该叶子入口单独启动采集，审阅后统一保存，不主动处理无关待采分支。
已存在的函数复用原节点与证据；撤销人工边保留节点和已有静态关系。

续采重新 prepare 待采符号、核对稳定 ID；每个完成请求原子保存检查点。停止会等待当前
查询结束。服务重启保留图中的 pending/queried，内存中的入口校验 token 需重新生成。
保存时比较原图，冲突停止。源码变化后应重新分析：旧图没有完整源码指纹，不能保证旧
关系仍有效。构建脚本和过程宏禁用，依赖 PATH 中 rust-analyzer。当前入口选择只支持
同项目 Rust，不支持跨项目消费者或自动识别异步消息路由。

本次理解问题：用户遇到异步边界时，能从源码确认接收函数并继续阅读，无需猜测采集参数。
北极星验收应让陌生项目读者在 10 分钟内定位一个异步入口、说明人工关联依据，并从
新入口验证后续调用。自动化仅验证操作与数据正确，不代替这一理解测试。


## 大图检查点开销（2026-11-02）

后端草稿检查点改为直接比较结构化图数据，避免每次创建四棵 JSON Value 树。
已知旧格式版本的输出等价规则不变；过期草稿仍拒绝覆盖，恢复原内容后 dirty 归零，
采集结果仍须用户显式保存才写入图文件。状态轮询不需要返回 graph 时，不再复制整图。
预算、排除、深度边界说明按一批调度合并检查点，成功查询仍逐个检查并保留。

以实际 Spring refresh 结果（2595 节点、3786 边）进行同进程 debug 对照，30 次检查点
比较和结果复制，旧 JSON 路径 5.766 秒，新结构化路径 0.154 秒。两侧都包含 after.clone()。
这是局部基准，不能换算成整轮采集加速倍数；JDT 查询、索引、每次图校验仍有耗时。
复现（输入只读）：

```powershell
$env:CODEROVA_BENCH_GRAPH='target/spring-refresh-timing-20261102/spring-refresh-lsp.json'
cargo test --target-dir target/coderova-parallel benchmark_checkpoint_comparison -- --ignored --nocapture
```

尚未取消按层调度屏障：慢查询仍可能推迟下一层，但保留该约束可以让有限预算下的
选点不依赖响应速度。下一轮应在固定源码、同等索引冷热条件下测量深层采集，分别记录
RPC、校验和检查点时间，再决定是否引入更复杂的调度或增量校验。

回归：Spring refresh 两层、预算 40、并发 4，本轮 14.840 秒，177 节点、229 边；
与上一轮 graph-4.json 完整 JSON 相等。前次 14.345 秒，未显示端到端提速，
且本轮与测试门禁同时运行，不作为严格耗时比较。CLI 不走页面 DraftStore，
这次真实采集主要验证语义和边界标记未改变。


## 协议和开源实现调研与后续改进（2026-11-02）

本轮默认 query timeout 调整为 15 秒，首次之外最多重试 3 次；初始化、索引就绪
使用独立期限。不能把它解释为整个节点最多 15 秒。取消是协作式的，客户端丢弃
迟到结果不代表服务端一定停止计算。

- [LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)：
  call hierarchy 支持 opaque data、取消和 partialResultToken。保留服务器 data 原样回传；
  partial results 需要服务端实际支持，不能只发一个 token 就宣称减少计算或可保存完整结果。
  本轮没有实现 partial result 接收，不发送该 token。
- [clangd 请求调度](https://clangd.llvm.org/design/threads)：按文件复用解析结果、
  丢弃取消工作、有界资源。已借鉴为单轮采集共享 documentSymbol 的按 URI single-flight：
  并发任务等待同一个 OnceCell，成功结果复用，失败不缓存，下一轮重新建立缓存，
  防止跨轮源码变化沿用旧符号；取消初始化不会留下永久等待状态。
- [clangd 索引](https://clangd.llvm.org/design/indexing)：文件粒度磁盘索引、动态层与后台层
  合并。长期可借鉴源码指纹绑定的查询事实缓存，但需包含服务端版本、配置和依赖变更，
  尚未加入磁盘结果缓存。
- [JDT issue 3886](https://github.com/eclipse-jdtls/eclipse.jdt.ls/issues/3886)：
  最初报告并发查询和全局锁造成慢查询，维护者和报告者后续确认 Zed 存在 prepare/cancel
  循环；原始单请求性能结论尚需重新测量。不能把 issue 标题作为本项目瓶颈的证明。
- [JDT CallHierarchyHandler 源码](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/master/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/CallHierarchyHandler.java)：
  prepare 清理 wrapper 缓存，outgoing 从 range.start 解析。当前声明位置归一化与身份验证
  保留；不能盲目删 prepare 或假设每个适配器都可安全复用 wrapper。

本机 graphify-custom/graphify/workbench.py 使用 snapshot 和文件 AST 缓存，先批量提取再
从索引遍历，不需要每条边通过独立语义 RPC 解析；这解释了一部分速度优势。其语法与
启发式解析没有执行与 JDT 相同的语义工作量，速度不能直接代表同等准确性。
本项目继续只用 LSP，借鉴缓存、去重与有界并行，不重新接入 AST 引擎。

正确性修复：Java 实现定位逐项隔离失败，保留已成功定位的实现和直接调用；只要实现
查询不完整，就保留 caller pending，并禁止把剩余一个实现自动当成唯一实现展开。
JDT 的排序异常与 NPE 属于上游错误，当前保留 issue 和源码位置，不将失败伪装为成功。

实测：Spring refresh 两层、预算40、并发4，新结果完整 JSON 与旧结果一致；
documentSymbol 133→79（减少40.6%），总耗时15.072秒，未观察到整体显著提速。
证据 target/spring-shared-symbols-20261102/。


## 公共采集器：合并已完成结果（2026-11-02）

这是应用层优化，不是 LSP 协议特性，Rust 和 Java 共用实现。
并发查询返回后，只取当前 JoinSet 中已经完成的结果，一次合并、一次复制图和检查点校验；
不等待仍执行的慢请求，不增加定时窗口，不改变按层预算选点或调用点证据。
一个批次内同步合并与检查点之间没有 await，任务取消不会插入半批处理。
传输失败仍先处理已经返回的成功事实，再标记未完成节点。
日志 LSP collector result batches 记录 completed、result_batches 和 largest_batch，
用于衡量实际节省的检查点次数；没有多个同时完成的结果时，行为与逐个处理相同。
新增回归验证同时完成的结果能合并、未完成工作不阻塞；完整门禁继续验证 Rust、Java、
预算、乱序、超时重试、取消、部分成功和草稿保存冲突。
本轮没有新的同规模 Spring 端到端性能数据，不据此宣称整轮提速。

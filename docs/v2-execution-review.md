# V2 执行理解迭代评估（2026-10-31）

本轮角色为前端维护，范围为 G6 V2、浏览器测试与本评估；未修改后端分析契约。
目标是让读者能从一次调用定位到双方方法、控制条件及源码证据，减少把静态关系误读为执行轨迹。

## 发现与本轮交付

- 调用点已经独立展示，但侧栏仍以通用调用标签为标题，不能直接说明双方身份。
  现在标题明确显示调用方 → 被调用方。
- 控制语义已存在于图数据，侧栏却未显式解释。现在展示条件分支、降级、汇合、回环、
  循环退出及已有条件；缺少条件时明确说明，静态调用标明控制流程尚未分析。
- 图和侧栏排序逻辑分散。本轮提取共享 callReading：全部带 order 才按已有顺序排列；
  否则同文件有效行号按行排列；跨文件或缺少位置保持原记录。文案区分阅读顺序与执行顺序。
- 保留原始源码 ID、调用点、递归终止与按需展开，不新增推断边，不修改图 JSON。

## 尚未解决的核心问题

1. LSP outgoingCalls 不是控制流分析。当前生成器 order 为空，缺少分支、循环和嵌套
   表达式的求值关系。仅增加行列排序无法得到完整同步执行模型。
2. 大图在同层密集扇出时仍可能视觉拥挤；当前几何与性能测试不构成任意图无重叠保证。
3. 尚未执行产品战略要求的多人、固定源码版本的 10 分钟理解基准，不能宣称理解效果达标。

## 下一阶段优先级

P0：生成端增加有源码证据的控制流分析，先限定 Rust 同步普通函数；必须覆盖 B/C/B 重复调用、
嵌套调用参数求值、if/match、循环和提前返回。宏、动态分发与异步保留未知边界。
先确定表达模型及契约，再按 agent-development-boundaries 的协议更新生成、验证和浏览器适配；
不能直接把行号写入已有 order 字段。

P1：针对真实 codex-cli-startup 图建立固定操作回放：定位入口、展开、逐调用点核对、返回上下文。
记录首次证据定位时间、错误追线和缩放次数；性能测试与理解测试分别报告。

P2：在上述证据与验收稳定后拆分 entry.js 的选择、侧栏与画布生命周期，避免在产品语义仍变化时
先进行大范围目录重构。

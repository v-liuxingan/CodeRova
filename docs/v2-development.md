# V2 源码分析与 G6 阅读器

全局架构见[当前系统设计](system-design.md)；各能力完成情况、最近验证与待办见
[开发进度](development-status.md)。本文保留 V2 的启动、分析与开发操作说明。

V2 现支持[按调用层级渐进展示](v2-progressive-rendering.md)：默认 50 层，边界节点可继续
展开后续 50 层；支持横/纵同层对齐、可选节点数量模式及完整图搜索。原始图数据保留。
默认使用调用路径视图，共享函数在不同分支下以独立引用展示；可切换调用关系视图检查
原始共享拓扑。重复子树按需展开，递归引用停止扩展，两者均使用 G6。

第一阶段已经实现可运行的纵向链路：可信本地 CLI → rust-analyzer → 带源码证据的
CallGraph JSON → 现有 HTTP 接口 → G6 Canvas → 定义与调用点预览。
主目标仍是让读者在 10 分钟内理解一个场景并核对源码。机器生成的静态图是分析底稿，
不是已经完成业务解释的场景图。

## 启动

```powershell
rustup component add rust-analyzer
npm ci
npm run build:frontend
cargo run -- serve --port 4322
```

访问 `http://127.0.0.1:4322/v2/`。经典工作台顶部也有 V2 入口。
项目列表、图选择、Canvas 和源码面板在同一页；支持图链接、历史前进后退与符号查找。
首次打开默认亮色，右上角可切换亮色/深色并保存偏好；切换只刷新样式，保留选择和视口。
默认不选择符号、不高亮链路；选择节点或关系后才突出相关路径。单击画布空白处清除选择和源码预览；拖拽（包括拖出再回到起点）不取消选择。切图与刷新回到未选择状态。
旧版场景阅读、布局存储等功能继续保留在经典工作台。V2 暂不保存手动拖拽布局。

## 从真实源码生成

项目必须先登记在 `callgraph.projects.json`。文件相对该项目根目录，行列均从 1 开始，
列以 UTF-16 单元计数，并指向函数名。示例入口目前在 `src/validation.rs:40`，源码修改
后须重新定位，不应盲目复用旧行号。

```powershell
cargo run -- analyze --project callgraph-visualizer --file src/validation.rs --line 40 --column 8 --max-depth 2 --request-budget 30 --output graphs/analysis/validation-local.json
```

输出文件必须不存在，避免覆盖已整理的图。生成后刷新 V2 即可发现它。使用
`cargo run -- validate <输出文件>` 和 `npm run check:content` 校验。
仓库提供 `callgraph-v2-validation` 真实结果供首次阅读，包含 4 个项目内符号和 5 个调用点。
这是当前源码、指定范围和配置下的实测结果，不是语言服务器完整性承诺。

`--server` 可指定 rust-analyzer 可执行文件，重复的 `--server-arg` 传递进程参数。
本阶段适配依赖 rust-analyzer 的索引就绪通知，不宣称兼容任意 LSP 服务器。
构建脚本与过程宏执行关闭，以避免首次分析运行项目脚本；此设置可能减少分析覆盖。

初始化/单次查询有超时；索引就绪等待最多 180 秒。Ctrl+C 取消并关闭会话，取消不导出图。
出向查询出现 null、错误或预算边界时，图内保留明确的待分析节点；查询中断后不会尝试
把残余响应当成新结果。输出文件创建冲突会失败。会话持有的 opaque `data` 原样传回 LSP。

## 数据与职责

- `src/analysis/lsp.rs`：stdio framing、请求关联、服务器反向请求、超时和子进程清理。
- `src/analysis/mod.rs`：项目内路径解析、调用点收集、环去重、深度/请求预算和导出。
- `CallGraph.analysis`：提供者、分析范围、预算、已查询/待查询符号、范围与失败说明。
- `static-call`：分析器报告的静态关系，机制未分类；不自动填条件、执行顺序或业务职责。
- `frontend/v2/entry.js`：G6 适配和阅读交互；`CallgraphApi` 仍是浏览器 API 边界。

静态查询返回空数组只表示服务器未报告下游。跨项目目标记录为边界说明，不伪造节点；
不同调用点分别保留为边。节点身份在相同源码快照上稳定，修改行列后可能改变。
配置格式独立于 G6；源码预览仍只接受图目标 ID，不接受浏览器提供的任意路径。

## 验证与下一阶段

`tests/lsp_analysis_test.py` 使用协议测试端验证真实 CLI 传输、循环、多调用点、预算、
opaque data、null/错误、能力缺失和防覆盖；不冒充真实语言服务器验收。
`tests/v2_e2e.py` 在真实 Rust 服务上验证 G6、源码预览、目录和浏览器历史。
两者均纳入 `python tests/run_e2e.py`，此外保留后端门禁和内容检查。

后续按验收结果推进：

1. 浏览器项目与入口选择、可取消分析任务、进度和结果导入；进程配置仍由后端可信配置管理。
2. 源码快照、缓存失效与稳定符号身份，再增加增量分析和续查。
3. 依据 Qoreon 技术栈验证第二种语言适配，明确框架关系缺口。
4. 业务解释、场景生成与动态关系补充，保留事实/推断来源。
5. 用相同真实图对比 G6 与旧版布局、拖拽、定位证据成本，再决定默认入口迁移。

本阶段没有完成上述后续能力，也没有通过换用 G6 宣称性能或理解效果已经达标。

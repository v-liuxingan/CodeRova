# Codex CLI 启动流程：真实项目分析验收

日期：2026-10-31。目标是用当前项目的 LSP 分析器与 G6 V2，分析 Codex CLI 启动并评价
产物质量、覆盖边界和实际性能。本轮没有修改分析器或渲染器，也没有运行 Codex 登录、
真实模型请求或迁移用户状态数据库。

## 1. 结论

**当前实现能生成有调用点证据的真实大图，但原始静态图还不能直接充当优质的启动流程说明。**
交互启动入口扩大预算后，4,144 个项目内符号全部完成查询，产生 8,688 条调用边。
这证明该入口的 LSP 静态查询在本配置下收敛，不证明跨语言、跨平台和动态运行行为完整。

人工核对的交互主干 14 个调用点，扩大预算后的原始图全部包含。默认启动的分支条件、
初始化顺序、数据库恢复循环和异步首帧语义仍需人工解释。大图的拖动和选择存在明显延迟，
不能因为采用 Canvas 就认为性能问题已经解决。

## 2. 验收对象与复现条件

- Codex 源码：`../codex`，提交 `a68d0a74bd38ddc01361ce42262da689b788afce`。
- 源码工作区存在既有 `codex-rs/metadata.json` 和 `codex-rs/learn-tech_outputs/` 状态；本轮不修改它们。
- 分析器：本项目当前工作区 `cargo build --quiet` 后的 debug CLI；非已发布版本。
- 语言服务器：`rust-analyzer 1.95.0 (59807616 2026-04-14)`；本机 Windows，build scripts 和 proc macros 关闭。
- 机器：AMD Ryzen 7 7800X3D，8 核/16 线程，约 31.65 GiB 可见物理内存。
- 浏览器：Playwright Chromium 145.0.7632.6，headless，1500×950，默认亮色。
- 阅读服务：`http://127.0.0.1:4322/`，真实 Rust API。

以“普通 `codex` 启动至交互首帧/事件循环”为主要场景，补充 npm 包启动、子命令分流、
resume/fork、远程/内嵌服务、引导取消、启动失败与退出行为。
其他子命令内部、服务端 ThreadStart 内部以及首轮模型执行不属于启动主干展开范围。
LSP 原始遍历会进入这些辅助函数及其他可达实现，因此其图范围比场景范围大。

## 3. 实际启动流程与源码事实

以下位置均相对 Codex 项目根。阅读图保留原生入口；npm 启动器单独说明，避免把
跨语言进程启动伪装为 rust-analyzer 自动识别的函数调用。

| 阶段 | 已核验的执行行为 | 主要源码依据 |
| --- | --- | --- |
| npm 入口（可选） | 按平台/架构选择发行包，寻找 native binary；缺失时给出重新安装提示。设置包管理器环境标识，继承 stdio 启动子进程 | `codex-cli/bin/codex.js:79`、`:195` |
| 信号与进程退出 | Node 包装层转发信号，按子进程退出码或信号结束；直接运行 native binary 不经过此层 | `codex-cli/bin/codex.js:213`、`:246` |
| 原生入口与别名分派 | 读取 remote-control 标志；arg0 区分普通 CLI 与沙箱/补丁等工具身份，准备环境及 PATH 别名 | `codex-rs/cli/src/main.rs:958`、`codex-rs/arg0/src/lib.rs:60` |
| 运行时 | 创建指定栈大小的 `codex-main` 线程，构造多线程 Tokio runtime；异步回调结束前保留路径守卫 | `codex-rs/arg0/src/lib.rs:214`、`:285` |
| 参数分流 | Clap 解析参数并合并 feature overrides；无子命令进入交互模式，resume/fork 也复用交互启动器；exec/review 等另行委托 | `codex-rs/cli/src/main.rs:966`、`:995`、`:1274`、`:1341` |
| 终端与恢复门禁 | 规范化 prompt 换行，检查 dumb terminal 和 TTY/确认条件，解析远程认证；状态库锁定或不可恢复错误终止，可恢复错误备份后重试，每路径不重复备份 | `codex-rs/cli/src/main.rs:2305`、`:2372` |
| 服务位置 | 显式远程优先；允许复用且发现默认 daemon 时复用，否则内嵌。不是三个服务顺序启动 | `codex-rs/tui/src/lib.rs:862`、`:979` |
| 配置和依赖 | 处理覆盖参数、CODEX_HOME、环境和 cwd；先读取引导配置再准备认证/云配置与有效配置，检查登录限制，准备状态库、日志与可选 OSS provider | `codex-rs/tui/src/lib.rs:911–1320` |
| 终端与服务启动 | 接管终端并设置恢复守卫；发布构建可走更新提示；连接/启动服务，失败则恢复终端 | `codex-rs/tui/src/lib.rs:1324`、`:1355`、`:1390`、`:452` |
| 登录与信任引导 | 需要认证或目录信任时进入引导；取消会关闭服务并还原终端，完成登录后可能重新加载配置 | `codex-rs/tui/src/lib.rs:1431–1518` |
| 会话选择 | 新建、恢复或分叉；选择器退出及恢复目标不可用有独立处理，不能把所有分支画成串行步骤 | `codex-rs/tui/src/lib.rs:1520–1705` |
| 首帧与后台线程创建 | App 取得启动依赖，新建分支 spawn `thread/start` 任务；聊天组件先排队提交。请求结果通过 `StartupThreadStarted` 回传，首帧调度不等同于线程请求已完成 | `codex-rs/tui/src/app.rs:767`、`:900`、`:637`、`:1135`；`codex-rs/tui/src/app_server_session.rs:1281` |
| 退出与清理 | App 返回后还原终端、结束会话日志；CLI 处理退出结果、用量/恢复提示及更新动作 | `codex-rs/tui/src/lib.rs:1837`、`codex-rs/cli/src/main.rs:734` |

节点内部的工具调用、配置加载细节、恢复/分叉协议内部在人工阅读图中按函数职责压缩；
其描述明确边界。阅读图没有冒充全仓库全调用展开，也没有用虚拟节点制造流程顺序。

这是连续单次运行，不是清空系统缓存的冷启动对照，不能据此断言第二轮更快。
第二轮通过约半秒间隔加进程枚举开销采样本次分析进程树，工作集峰值
7,176,433,664 bytes（约 **6.68 GiB**）；这是采样峰值，不是精确内存分配峰值。

## 5. 产物质量评估

| 维度 | 观察 | 判断 |
| --- | --- | --- |
| 定位有效性 | 图校验通过；核验版的节点声明和调用点逐项对照源码，浏览器源码预览可用 | 可作为可追溯的分析底稿 |
| 主干覆盖 | 总入口图包含核验清单 21/22 节点、22/23 调用点，缺 `spawn → thread/start`；交互收敛图覆盖其范围内 14/14 个清单调用点 | 小型主干清单覆盖较好；不是全部 8688 条边的准确率统计 |
| 语义解释 | 自动边均为 `static-call`，没有条件、已证实顺序或业务阶段；节点职责为占位解释 | 原图不能独立回答默认路径为何如此执行 |
| 异步和恢复 | 调用存在不等于说明 Tokio spawn、启动结果事件、数据库重试和终端清理语义 | 需要源码证据支撑的解释层 |
| 范围完整性 | 待查询为 0；JS 包装层、禁用宏/构建脚本、平台条件和动态行为仍在范围之外 | 不能标成“完整真实执行链” |
| 证据精度 | 保存符号起始行和调用行，调用列在 evidence 文本中；节点未保存完整定义 endLine | 可定位，但不足以直接阅读整段复杂实现 |
| 结果置信度 | 自动边 confidence 为 1，实际表达的是服务器报告关系，而非动态执行的绝对确定性 | 需要澄清置信度含义，避免误读 |
| 可扫读性 | 大量同名 `new`、`run` 等符号，无业务短描述；初始聚焦根节点后下游散布在屏外 | 当前原图不适合直接完成 10 分钟理解任务 |

以上为作者源码审查和自动化观测，**没有完成至少 5 位陌生读者的正式理解测试**，
不计算产品北极星通过率，也不以人工核验图的简洁性替代原始关系的保留。

## 6. 浏览器性能

测试用临时 bundle 暴露图实例及 `renderer.render()` 计时，未改生产入口。
实际鼠标拖动节点 120×50 px、30 次插值；帧 P95 是该动作期间 requestAnimationFrame
间隔，样本少，不等同于长时间稳定 FPS。选择耗时包含符号选择、聚焦、高亮及源码展示，
不是单独的 HTTP 耗时。测量脚本和 JSON 保留以便复测。

排除并行 LSP 分析后的复测基线：

| 图 | 页面至可操作 | render 调用 | 拖拽帧间隔 P95 | 选中至源码显示 |
| --- | --- | --- | --- | --- |
| 人工核验 22 节点/23 边 | 572 ms | 41 ms | 16.8 ms | 21 ms |
| 总入口 2040 节点/3562 边 | 6790 ms | 3195 ms | 100 ms | 3297 ms |
| 交互收敛 4144 节点/8688 边 | 33746 ms | 16447 ms | 333.4 ms | 16605 ms |

两张图拖拽最终位移均正确，没有浏览器异常或源码错误；但大图连续拖拽约 3.74 s，
小图同样动作约 0.50 s，体现出明显的输入处理延迟。首次测量大图结果接近：
可操作 6654 ms、帧 P95 99.9 ms、选择 3297 ms。

交互收敛图同样没有浏览器异常、源码错误或最终位移偏差，但 30 次插值拖拽耗时
11.41 s，页面 DOM 达 18,122 个。这一规模下交互已不可接受；不能以“最终位置正确”
判定跟手性能通过。完整图测量只有一次，不据此提供统计稳定性保证。

从代码可以确定的优化候选：

1. `select()` 对每个遍历到的节点重新扫描全部边，接近 O(V×E)；应预建双向邻接索引。
2. 选择/取消向全部节点和边提交状态，且调用可能触发大范围更新；应测量状态更新耗时并仅提交变化。
3. 折叠的边界说明仍逐条创建 DOM；2040 节点图页面约 6762 个 DOM 元素，应按需渲染和归类。
4. 图布局、视口操作和拖拽渲染需分别分析；初始根节点可读但周围上下文远离屏幕，不能只靠最小缩放阈值解决。

这些是代码证据支持的候选，不冒充已经完成 CPU profile 的单一根因结论。

## 7. 验收与后续优先级

本轮新增内容使用现有 schema 和渲染器，没有修改运行时代码。执行结构/源码位置校验和
Codex 内容检查：全部 20 张调用图的结构/源码位置校验通过；Codex 范围 15 张调用图、2 张场景、19,020 个源码位置检查通过。缺少源码指纹基线的警告保留，不自动创建基线来消除警告。
截图、原始 JSON、命令和指标分别存档；未运行完整应用回归或后端 clippy，因为未修改实现。

建议下一轮优先处理：

1. 建立这两档真实图的可复现性能基线，先优化邻接索引、状态差分、边界列表按需渲染，再评估布局与 Canvas 重绘。
2. 分析结果区分“查询已完成”和“执行语义已解释”，保存运行配置、源码版本、目标平台和每阶段耗时。
3. 保留完整原始图，提供有证据的启动阅读层；默认路径、互斥分支、恢复和异步边界应可追溯到原始符号/调用点。
4. 用陌生读者验证从 npm/native 入口到首帧及 thread/start 的理解，重点检查是否错误地把互斥服务路径、初始化完成和线程创建完成当成同一顺序链。

# Callgraph Visualizer 计划

本路线图服务于项目的[产品战略](product-strategy.md)。标准 JSON、图渲染、源码预览和
静态分析接入都是实现战略目标的手段，不是项目成功本身。

## 1. 背景

阅读大型源码仓库时，调用链经常跨越多个模块、包、进程和服务。仅通过文件路径和行号
阅读，难以快速理解节点之间的走向，尤其容易遗漏闭包回调、接口或 Trait 分发、异步
任务边界和远程调用。

Codex 的 TUI 授权链被选为第一条真实验证链，但工具的数据模型、后端和渲染器不依赖
Codex，也不限定 Rust 项目。

本项目计划构建一个基于源码证据的项目执行理解工作台，将调用分析结果转换成可探索、
可解释、可验证的执行模型。

## 2. 目标

### 2.1 战略目标

让开发者面对陌生项目时，能在 10 分钟内建立一个可验证的执行心智模型。

完成一次关键场景阅读后，用户应当能够正确说明：

- 这段流程为什么存在。
- 一次完整执行经历哪些主要阶段。
- 主干、分支、循环、异步、回调和汇合如何发生。
- 关键数据和状态如何变化。
- 上述结论分别由哪些源码证据支持。

### 2.2 产品能力

- 用标准 JSON 描述一条或多条调用链。
- 将调用关系组织为有阅读顺序和控制流语义的交互式执行图。
- 节点解释局部职责以及它在完整流程中的作用。
- 连线解释调用方向、控制流、状态传递和跳转代码位置。
- 支持节点展开、折叠、隐藏和上下游聚焦。
- 让重要结论可以回到真实源码验证。

### 2.3 非目标

- 第一阶段不追求完整、无误差的 Rust 全量静态调用图。
- 第一阶段不替代 rust-analyzer、IDE 调用层次或调试器。
- 不把所有宏展开、泛型实例化和动态分发都强行伪装成确定调用。
- 不成为通用 UML、流程图或自由画布编辑器。
- 不以节点数量、连线数量或视觉复杂度衡量产品价值。
- 不要求用户通过大量按钮和人工配置才能看懂一条流程。

## 3. 典型调用链

第一条验证链使用当前正在学习的 TUI 授权链：

```text
main
  -> run_interactive_tui
  -> codex_tui::run_main
  -> start_embedded_app_server
  -> InProcessAppServerClient::start
  -> codex_app_server::in_process::start
  -> AuthManager::shared_from_config
  -> ModelProvider::auth
  -> auth_provider_from_auth
  -> BearerAuthProvider
  -> AuthProvider::apply_auth
```

## 4. 数据模型

建议以 `callgraph.json` 作为标准交换格式：

```json
{
  "schemaVersion": "0.2",
  "projectId": "codex",
  "title": "TUI authorization call graph",
  "root": "cli.main",
  "nodes": [
    {
      "id": "cli.main",
      "kind": "function",
      "label": "main",
      "crate": "codex-cli",
      "file": "codex-rs/cli/src/main.rs",
      "line": 956,
      "endLine": 962,
      "role": "CLI 程序入口",
      "description": "启动 CLI 并进入异步命令分发流程",
      "state": "expanded"
    }
  ],
  "edges": [
    {
      "id": "edge.cli-main-to-tui",
      "from": "cli.main",
      "to": "cli.run-interactive-tui",
      "kind": "direct",
      "label": "调用",
      "file": "codex-rs/cli/src/main.rs",
      "line": 2273,
      "description": "CLI 将交互启动委托给 TUI crate"
    }
  ]
}
```

### 4.1 节点字段

- `projectId`：图所引用的稳定项目标识；实际根目录由项目目录配置解析。
- `id`：稳定标识。
- `kind`：函数、结构体、Trait、模块、进程、远程服务等。
- `file`、`line`、`endLine`：源码定位。
- `role`、`description`：面向学习者的职责说明。
- `state`：展开、折叠或隐藏状态。

### 4.2 连线字段

- `from`、`to`：起点和终点。
- `kind`：`direct`、`callback`、`trait-dispatch`、`spawn`、`remote` 等。
- `file`、`line`：发生跳转或调用表达式的位置。
- `confidence`：对间接调用分析结果的可信度。

底层使用图结构，不强制限制为树，因为一个函数可能有多个调用者，也可能形成循环。界面可以在图之上提供树状展开视图。

## 5. 交互设计

- 节点：显示函数名、crate、源码行号和一句职责说明。
- 连线：显示调用类型和 `文件:行号`。
- 点击节点：显示详细信息，并提供“跳转 VSCode”。
- 点击连线：定位调用发生处，而不是只定位目标函数。
- 展开/折叠：以节点为边界隐藏或显示下游子图。
- 隐藏：临时移除噪声节点，但保留其关系数据。
- 聚焦：保留完整图，强调选中节点的相关上下游路径并弱化无关内容。
- 间接调用：使用不同样式标识闭包、Trait、异步任务和远程边界。

## 6. VSCode 跳转方案

浏览器通过 VSCode 注册的外部协议打开源码：

1. 页面向本地服务提交调用图 slug、目标类型和 ID。
2. 服务端读取图的 `projectId`，从项目目录配置解析当前项目根路径。
3. 服务端拼接项目内相对路径，并验证规范化路径仍位于对应项目根目录内。
4. 服务端返回 `vscode://file/<path>:<line>:<column>`。
5. 前端在用户点击上下文中将 URI 交给浏览器。

服务端不启动 PowerShell、`cmd.exe`、`Code.exe` 或隐藏子进程。CLI 的 `open` 命令只输出
经过相同校验的 URI。未来可以通过 `SourceLinkBuilder` 增加其他编辑器协议。

## 7. 分阶段计划

### 阶段一：手工数据验证

- 手工编写当前 TUI 授权链 JSON。
- 验证节点、连线、文件行号和职责说明。
- 验证 VSCode 批量打开多个节点。

### 阶段二：交互式图渲染

- 实现本地 HTML/SVG 图视图。
- 支持方向箭头、节点选择、展开、折叠和隐藏。
- 支持节点详情和连线详情。

### 阶段三：跳转工具

- 实现可替换的外部编辑器 URI 生成器。
- 支持节点跳转和连线调用点跳转。
- 增加 Windows verbatim path、空格、URI 保留字符和行号校验。
- 禁止服务端启动 shell、命令脚本或编辑器子进程。

### 阶段四：分析结果生成

- 根据源码阅读结果生成 JSON。
- 记录直接调用和间接调用的证据。
- 为 Trait、闭包、`tokio::spawn` 和 App Server 边界增加类型标记。

### 阶段五：学习流程集成

- 每节源码课保存一份调用链。
- 从学习笔记链接到对应调用图。
- 支持从节点发起“解释这个函数”或“继续追踪下游”的学习动作。

### 阶段六：理解效果验证

- 建立固定的真实项目关键场景、源码事实清单和测试说明。
- 按产品战略中的 `0–2` 分规则执行首轮 10 分钟理解任务，记录完成率基线。
- 记录证据定位时间、错误推断和阅读迷失点，区分内容问题、交互问题与生成问题。
- 将理解效果回归纳入重要版本验收，达到 `80%` 正式基准完成率。

## 9. 设计原则

- 先保证源码位置准确，再追求图形美观。
- 所有边都必须能说明“为什么认为存在这条调用关系”。
- 不确定的间接调用必须显式标记，不伪装成确定事实。
- 图用于帮助阅读源码，不能替代源码本身。
- 工具输出应适合长期积累和后续自动生成。
